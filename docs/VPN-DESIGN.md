# Prizrak VPN — технология «Призрак-Транспорт»

Документ описывает, как устроен обход блокировок в Prizrak VPN и что мы делаем
по этапам. Главная задача: пользователь в РФ подключается и работает так, чтобы
ТСПУ **не смог отличить** его трафик от обычного веба — ни по сигнатурам, ни по
активному зондированию, ни по статистике.

---

## 0. Чему мы противостоим

ТСПУ (и подобные системы) блокируют по четырём признакам. Любой из них
достаточно, чтобы нас порезали:

| Признак | Что именно смотрят | Кого убивает |
|---|---|---|
| **Сигнатуры** | Магические байты, структура хендшейка, отпечаток TLS ClientHello | WireGuard, L2TP/IPsec, OpenVPN, Shadowsocks старых версий |
| **Активное зондирование** | Цензор сам стучится на подозрительный IP и смотрит ответ | Всё, что отвечает «не как сайт» |
| **Статистика** | Размеры пакетов, тайминги, направление, длительность сессии, **TLS-in-TLS** | VLESS/Trojan/Reality — детектируются по вложенным TLS-записям |
| **Адреса** | Диапазоны зарубежных VPS, домены, SNI | Любой сервис с фиксированным списком адресов |

Из этого следует главное правило дизайна:

> **«Свой протокол» ≠ «случайные байты».** Поток чистой энтропии на 443 порту —
> это тоже отпечаток, и он ловится тривиально. Наш протокол должен быть своим
> внутри и **по-настоящему обычным снаружи**.

## 1. Эстафета: два прыжка вместо одного

```
  Пользователь (РФ)                Узел-Приманка (РФ)            Узел-Выход (за границей)
  ┌──────────────┐   личина+тень   ┌───────────────┐   тень      ┌────────────────┐   обычный
  │  Prizrak     │ ══════════════▶ │  настоящий    │ ══════════▶ │   выход в      │ ─────────▶ Интернет
  │  «Замаскир.» │  российский IP  │  сайт + туннель│ сервер↔сервер│   интернет     │
  └──────────────┘                 └───────────────┘             └────────────────┘
```

**Зачем два прыжка:**

* Для ТСПУ трафик пользователя идёт **на российский адрес** — это самый обычный
  паттерн, а не «клиент из РФ непрерывно льёт на зарубежный VPS».
* Участок «приманка ↔ выход» — это трафик **между серверами**, а не «домашний
  пользователь → заграница». Его форма и объём выглядят как обычный обмен
  между сайтом и его бэкендом/CDN.
* Приманок можно поднимать десятками, они дешёвые и одноразовые.

**Слоистое шифрование** (как в onion, но два слоя вместо трёх):

* Клиент шифрует полезную нагрузку на ключ **выхода**, затем весь этот блок —
  на ключ **приманки**.
* Приманка снимает свой слой и видит только «переслать на выход N». Она **не
  знает**, к какому сайту вы идёте, и не может прочитать содержимое.
* Выход видит назначение, но **не видит IP клиента** — для него источник это
  приманка.
* Итог: чтобы связать «кто» и «куда», нужно скомпрометировать оба узла сразу.

### Как это сделано в коде (Этап 3)

`packages/vpn/src/estafeta.js` — три вложенные сессии «Тени» луковицей:

```
   клиент(РФ) ──сессия A──► реле/приманка(РФ) ──сессия B──► выход ──► сайт
              └────────────── сессия C (насквозь, клиент↔выход) ───────┘
```

* **A** (клиент↔реле) — то, что видит провайдер клиента: обычный сайт-личина.
* **B** (реле↔выход) — то, что видит провайдер реле: тоже обычный сайт,
  «сервер↔сервер».
* **C** (клиент↔выход) — настоящий туннель. Едет ВНУТРИ A, реле переупаковывает
  его в B, не читая. Ключей C у реле нет — расшифровать нельзя даже теоретически.

Управляющий протокол внутри A (`OP.LINK` / `LINK_OK` / `DATA` / `CLOSE`):

1. Клиент поднимает A с реле (через «Личину» реле).
2. Клиент шлёт `LINK{ exit:{host,port}, hs: <рукопожатие C> }`. Реле узнаёт
   **адрес выхода** (это неизбежно — ему туда звонить), но не назначение.
3. Реле дозванивается до выхода (поднимает B через «Личину» выхода) и прокидывает
   рукопожатие C **вслепую**. Выход достраивает сквозную сессию C с клиентом.
4. `DATA`-кадры: клиент шифрует нагрузку в C (видит только выход), потом в A
   (видит только провод). Реле пересылает непрозрачный C-кадр в B.

Роли в коде: `openCircuit` (клиент), `makeRelayPump` (слепой пересыльщик),
`makeExitEnd` (конец цепочки, только он расшифровывает C и видит назначение).

Тест `test/estafeta.mjs` — 13 проверок, включая доказательства приватности:
назначение видит только выход; в доступном реле кадре назначения нет и реле не
может его расшифровать; в кадрах к выходу нет адреса клиента; подмена и повтор
внешнего рукопожатия отвергаются.

**Что осталось на этап полевой сборки:** реальные сокеты между реле и выходом
(здесь смоделированы в памяти) и подъём реле/выхода как настоящих HTTP-серверов —
идёт вместе с «Личиной» на этапе 8.

## 2. Личина: снаружи — настоящий сайт

Ключевая идея, отличающая нас от «ещё одного VPN»: узел-приманка — это **не
замаскированный VPN, а настоящий работающий сайт**, у которого есть скрытая
дверь.

* На узле поднят реальный сайт с реальным сертификатом Let's Encrypt и
  осмысленным содержимым (документация, файлопомойка, галерея — что угодно
  скучное и легальное). Он реально открывается в браузере, индексируется,
  отдаёт картинки.
* Туннель — это **запросы к тому же сайту**: HTTP/2 POST с длинным телом,
  скачивание «файлов», WebSocket. На проводе это неотличимо от того, как
  человек пользуется этим сайтом.
* **Probe-resistance по-настоящему:** если пришедший не доказал знание ключа —
  он получает не заглушку, а **настоящий сайт**. Цензор, который стучится с
  зондом, видит обычный веб-ресурс и уходит. Отличить «сайт» от «сайта с
  туннелем» снаружи невозможно.

**Три несущие** (клиент умеет все, выбирает по обстановке):

| Несущая | Когда | Плюс / минус |
|---|---|---|
| **HTTP/2 внутри TLS** | По умолчанию | Самый обычный трафик; отпечаток ClientHello копируем с Chrome |
| **HTTP/3 (QUIC)** | Где не режут UDP | Труднее для DPI, меньше следов; ломается там, где UDP заблокирован |
| **WebSocket** | Корпоративные сети, прокси | Проходит там, где есть HTTP-прокси; чуть заметнее |

Если несущая начала «залипать» (растёт потеря, рвутся сессии) — клиент
**сам переключается** на другую и запоминает, что в этой сети работает.

### Как это сделано в коде (Этап 2)

Три модуля в `packages/vpn/src/`:

* **`site.js`** — сама личина: настоящий сайт (главная, статьи, CSS, RSS, форма
  обратной связи). Обработчик сайта **не знает про туннель** — он честно
  отвечает на любой запрос так, как ответил бы обычный сервер. Это принципиально:
  раз отдельного кода «для зонда» нет, то и отличить нельзя.
* **`carrier.js`** — несущие и укладка. `makeCarrierPicker` держит текущую
  несущую, помнит рабочие/сбоившие в этой сети, при деградации возвращается на
  проверенную или пробует новую (а если UDP блокируют — H3 вообще не предлагает).
  `packFrames`/`readFrames`/`makeFrameReader` кладут кадры «Тени» в тело HTTP с
  префиксами длины; поверх работает «Дыхание» — наружу тело нарезано под
  естественные размеры, не одним куском.
* **`lichina.js`** — привратник `makeDoorman`. Каждый запрос сначала сюда.
  Дверь живёт только за одним обычным endpoint'ом (форма). Тело POST узел
  **пробует** разобрать своим приватным ключом через `nodeHandshake`:
  сошлось AEAD-доказательство — это наш клиент, поднимаем «Тень»; не сошлось —
  отвечаем как форма («Спасибо!»). Зонд с мусором и человек с сообщением
  получают **одно и то же**. Повтор перехваченного тела дверь не открывает —
  срабатывает антиповтор «Тени».

Тест `test/lichina.mjs` — 25 проверок: сайт отдаёт контент, зонд получает форму,
наш клиент проходит и дальше работает end-to-end, повтор отлетает, кадры
укладываются и переупаковываются «Дыханием», несущая переключается при сбое.

**Что осталось на реальную сеть (не покрыто юнит-тестом):** поднятие настоящего
HTTP/2/H3-сервера с сертификатом Let's Encrypt и копирование отпечатка
ClientHello под Chrome (в Node штатно недостижимо — нужен свой TLS-стек или
внешний фронт вроде подобранного nginx/uTLS-прокси). Это выносится в этап
полевой сборки узла.

## 3. Тень: свой хендшейк и своё шифрование

Внутри личины — полностью наш протокол. Никаких заимствованных.

**Хендшейк (без единого магического байта):**

1. Узел заранее публикует свой X25519-ключ — он приходит клиенту вместе со
   ссылкой-приглашением (через сам мессенджер, по E2E).
2. Клиент шлёт эфемерный X25519-ключ, замаскированный под обычные данные
   запроса (тело POST / значение cookie-подобного поля).
3. Вместе с ним — AEAD-доказательство: метка времени + одноразовое число,
   зашифрованные на общем секрете. **Повтор записанного трафика не работает:**
   узел ведёт окно свежести и список использованных чисел.
4. Не сошлось — узел молча отдаёт настоящий сайт. Никакого «ошибка авторизации».

**Шифрование потока:**

* ChaCha20-Poly1305 (уже используется в проекте), ключи через HKDF, **разные
  ключи в каждую сторону**.
* Перемотка ключей каждые N мегабайт и каждые N минут — компрометация ключа
  не раскрывает всю сессию назад.
* Свой фрейминг: длины кадров **не совпадают** с границами внутренних TLS-записей.
  Это прямая защита от детекта TLS-in-TLS, на котором сейчас палятся
  VLESS/Trojan/Reality.

## 4. Дыхание: форма трафика

То, чего нет почти нигде, и то, чем ТСПУ ловит «правильно замаскированные»
протоколы. Мы управляем формой потока:

* **Паддинг под естественное распределение.** Размеры кадров подгоняются под
  то, как выглядит реальный сайт (много мелких + редкие крупные), а не под
  ровные 1400 байт.
* **Джиттер и склейка.** Мелкие пакеты собираются, отправка чуть «дрожит» —
  убираем машинную регулярность.
* **Профили:** «сёрфинг», «видео», «тихий фон». Клиент выбирает автоматически
  по характеру нагрузки; при простое — редкие поддерживающие кадры, чтобы
  сессия не выглядела как «висит открытой, но молчит».

### Как это сделано в коде (Этап 4)

Кирпичи формы лежат в `packages/vpn/src/shaping.js` (профили, нарезка, паддинг,
джиттер), а насос живого потока — в `packages/vpn/src/breath.js`. Через него
проходит весь трафик сессии:

* Кадры «Тени» заворачиваются в служебную рамку с типом (`DATA` / `PAD` / `KEEP`).
  Паддинг — это ОТДЕЛЬНЫЙ тип кадра, а не мусор в хвосте: поэтому он обратим и не
  ломает разбор следующих кадров.
* Поток режется «Дыханием» на куски естественного размера — границы кадров «Тени»
  наружу не проступают.
* В паузах насос сам «дышит» `KEEP`-кадрами (по расписанию профиля), чтобы
  долгоживущая сессия не висела молча — молчащий часами TLS сам по себе
  подозрителен. `KEEP` на приёме отбрасывается.
* Профиль (сёрфинг / видео / тихий фон) выбирается по нагрузке НА ЛЕТУ:
  встроенный счётчик за скользящую секунду кормит `pickProfile`.
* `flush()` досылает хвост из переупаковщика, когда очередь отправки опустела
  (иначе последний кадр застрял бы в буфере).

Тест `test/breath.mjs` — 15 проверок: DATA проходит насквозь при любой нарезке
провода, PAD/KEEP отбрасываются, узор 16384 не проступает, keepalive приходит
только после паузы, профиль сам переключается под нагрузкой, кадр «Тени»
переживает форму и расшифровывается.

> **Побочно найден и исправлен баг** в `shaping.js`: переупаковщик брал размер
> куска через `chunkSizes(1,…)`, а тот из-за `min(1, size)` всегда возвращал 1 —
> поток вырождался в однобайтовые куски (само по себе яркий отпечаток). Введён
> `nextChunk()` — «естественный» размер без привязки к остатку.

## 5. Стая: живучесть адресов

Блокируют не протокол, а адреса. Поэтому:

* Список приманок **нигде не публикуется**. Клиент получает свой набор через
  сам мессенджер (E2E) или через **сеть тайников**, которая в проекте уже есть.
* У каждого клиента свой небольшой набор адресов → «сожжённый» адрес выдаёт
  лишь малую группу, а не всех сразу.
* Автозамена: узел перестал отвечать → клиент тихо берёт следующий и просит
  пополнение набора.
* Домены обычные, разные, с настоящими сайтами. Единого «домена VPN» нет.

### Как это сделано в коде (Этап 5)

`packages/vpn/src/flock.js` — две стороны раздачи:

**Директория** (сторона сервиса):

* `assignSet({pool, clientId, epoch, k, secret})` — какие узлы выдать клиенту.
  Каждому узлу считается псевдослучайный «балл» = `sha256(secret ‖ clientId ‖ epoch ‖ nodeId)`,
  берутся `k` с наименьшим баллом. Свойства: детерминировано (стабильно внутри
  эпохи), но **без секрета директории не воспроизвести** — клиент не предугадает
  чужой набор и не перечислит пул из алгоритма. Разным клиентам — разные наборы
  с малым пересечением; в новой эпохе набор ротируется.
* `packShare(secret, node)` — подписанная Ed25519 «доля»: один узел (id, ключ,
  адреса, роли, страна, эпоха). Это E2E-контент внутри мессенджера/тайника, без
  «магии» протокола на проводе.

**Клиент**:

* `readShare(bytes, trustedPubs)` — принять долю только от доверенной директории;
  подделка и мусор отвергаются.
* `makeAddressBook()` — хранит выданные узлы, помнит сожжённые, отдаёт следующий
  пригодный (`next`), сигналит `needsRefill()` когда живых почти не осталось и
  `staleEpoch()` когда пора обновить набор.

**Защита от перечисления** (проверено тестом): цензор, поднявший 20 ложных
клиентов, собирает меньше 40% пула — мало адресов на клиента (k=3) плюс секретное
распределение не дают вычерпать список. Это тот же приём, что у мостов Tor.

Тест `test/flock.mjs` — 26 проверок. Транспорт раздачи (мессенджер / сеть
тайников deaddrop) в проекте уже есть — переиспользуем, здесь только логика
набора, доверия и автозамены.

## 6. Экономика: узлы и награды

* **Билеты доступа** — подписанные Ed25519 разрешения (издатель — Банк
  Призраков или сам владелец узла). Узел проверяет подпись локально, в Банк
  на каждое подключение не ходит и **не знает, кто вы**: в билете только
  непрозрачный идентификатор и лимиты.
* **Награды операторам** — за аптайм и прокачанный трафик, в призраках 👻.
  Механика уже работает для узлов-тайников, переиспользуем её.
* Свои серверы + чужие узлы: сеть растёт сама.

## 6a. Тариф: цена в админке Банка

Подписка на VPN продаётся за призраков, цену задаёт владелец в админке Банка —
как уже сделано для наград операторам и цен подарков.

**Что настраивается (`/admin` → раздел VPN):**

| Параметр | Смысл | Пример |
|---|---|---|
| Цена подписки | Сколько 👻 за период | `150` |
| Период | На сколько выдаётся билет | `30 дней` |
| Лимит трафика | 0 = без лимита | `0` или `200 ГБ` |
| Тарифы (опционально) | Несколько уровней: базовый / без лимита | `basic 150`, `pro 400` |
| Пробный период | Бесплатные дни новым | `0` или `3 дня` |

**Как это работает вместе с билетами:**

1. Пользователь жмёт «Замаскироваться» → приложение проверяет, есть ли живой
   билет. Нет — предлагает купить за 👻 из кошелька.
2. Банк списывает цену и **выписывает билет** (подпись Ed25519, срок = период,
   лимит трафика из тарифа).
3. Узлы проверяют билет **локально по подписи** — в Банк на каждое подключение
   не ходят и не знают, кто вы.
4. Срок вышел — приложение молча просит новый билет; денег не хватило — честно
   пишет об этом и выключает маскировку.

Смена цены в админке действует на **будущие** покупки: уже выписанные билеты
доживают свой срок.

### Делёж выручки

Деньги с подписки делятся между **оператором выходного узла** и **владельцем
сервиса**. Доля тоже задаётся в админке:

| Параметр | Смысл | По умолчанию |
|---|---|---|
| Доля оператора выхода | Сколько 👻 от подписки уходит тому, чей узел выпускал трафик | `50%` |
| Доля сервиса | Остаток — владельцу платформы | `50%` |
| Доля приманки (опц.) | Если хотим платить и промежуточным узлам | `0%` |

Правило работает **сразу, ещё до открытия сети для чужих узлов**: наши
собственные выходы тоже «зарабатывают» свою долю. Это нужно не ради перекладывания
денег из кармана в карман, а чтобы:

* учёт трафика и начисления были **обкатаны на живых деньгах** до того, как
  придут чужие операторы;
* в любой момент можно было включить пользовательские узлы, не трогая код —
  только политику;
* сразу видеть в отчётах, сколько стоит каждая страна и какой узел окупается.

**Как считается доля.** Подписка — это период, а трафик размазан по узлам и
странам (пользователь переключался между Францией и Швецией). Поэтому выручка за
период делится **пропорционально прокачанному трафику**: узел, через который
прошло 70% байтов пользователя, получает 70% операторской доли. Данные берутся
из тех же отчётов узлов, что уже используются для наград — новый механизм не
нужен.

Изменение процентов действует на **будущие** начисления; уже посчитанные
периоды не пересчитываются.

## 7. Два переключателя в приложении

Prizrak становится основным приложением для доступа к сети:

**«Замаскироваться»** — весь трафик устройства идёт через Призрак.
* Android: системный VpnService (tun-интерфейс) — трафик всех приложений.
* Десктоп: tun-интерфейс (macOS/Windows) + режим прокси как запасной.
* Внутри устройства это tun/локальный вход — **на провод не выходит**, по сети
  идёт только наш протокол.

**«Поднять призрак-узел»** — устройство/сервер становится частью сети.
* Роли: приманка (РФ) или выход (заграница) — задаётся при включении.
* Учёт трафика и начисление призраков автоматически.
* На телефоне — только лёгкий режим (приманка), выход требует стабильного канала.

### Как это сделано в коде (Этапы 6–7)

**Движок** `packages/vpn/src/engine.js` — оркестратор, связывающий все слои:
`makeEngine` держит состояние (`off/connecting/up/switching/searching`), выбирает
реле и лучший по рейтингу выход в стране, поднимает цепочку через `connect(...)`,
переключается по сигналу «Живучести» (`onExitFailed` → узел той же страны →
соседняя страна) и **никогда не пускает трафик в обход туннеля**: `send` бросает,
пока состояние не `up` (лучше нет связи, чем голый IP). Смена страны на лету —
`switchCountry` по правилу make-before-break с откатом. Тест — 20 проверок.

**Страны и рейтинг** — `countries.js` (реестр, флаги, соседи, проверка страны по
GeoIP наблюдаемого адреса — не по заявке оператора; `countryList` для UI) и
`ratings.js` (Байесово среднее, свежесть 60 дней, антинакрутка: только с
оплаченного билета, раз в сутки; узлы ниже 2.5 скрываются; вывод «4.35 из 5»).
Тест — 21 проверка.

**Экономика** — `economy.js`: `splitRevenue` делит выручку (по умолчанию 50/50,
проценты из админки) пропорционально прокачанному трафику, «пыль» округления
уходит сервису, сумма сходится до призрака; `makeUsageMeter` считает байты по
узлам. Тест — 14 проверок. В Банке (PHP): страница `/admin/vpn` задаёт цену
подписки, проценты делёжа (сумма всегда 100%), порог скрытия по рейтингу и флаги
`allowCommunityRelays` / `allowCommunityExits` (выходы по умолчанию ВЫКЛ).
Таблицы `vpn_nodes` / `vpn_ratings`, публичные `GET /api/vpn/countries` и
`POST /api/vpn/rate`.

**UI обеих платформ** — мобилка (экран «Призрак-VPN»: два переключателя + выбор
страны со звёздами «4.35 из 5», `packages/mobile/App.jsx` + мост
`src/native/vpn.js`) и десктоп (секция настроек VPN, `renderer/` + `lib/vpn.js` +
preload-мост). Страны с рейтингом тянутся из Банка (`client.vpnCountries()`).

**Нативный слой** — Android `PrizrakVpnService` (Kotlin): `VpnService.Builder`
с `addDisallowedApplication(нашего пакета)` — свой трафик мимо туннеля, foreground,
запрос разрешения; RN-модуль `PrizrakVpnModule` (maskOn/off, switchCountry,
nodeOn/off, status, события). Десктоп — каркас `lib/vpn.js` с описанием tun по ОС.
**Насос пакетов tun ↔ движок и реальный TLS-фронт — полевая работа этапа 8**
(движок и все слои уже покрыты тестами).

## 7a. Что НЕ идёт через туннель

**Собственный трафик Призрака — сообщения, звонки, синхронизация — идёт мимо
VPN, напрямую, как сейчас.**

Это не только про удобство. Приложение, которое строит туннель, физически не
может ходить внутрь него: получилась бы петля (пакет туннеля → снова в туннель
→ …). Поэтому исключение своего трафика — обязательное условие работы, а не
опция.

Что ещё это даёт:
* **VPN упал — сообщения ходят.** Мессенджер не зависит от состояния туннеля.
* **Нет двойной обёртки.** Наш транспорт уже стелс; заворачивать его ещё раз —
  это лишняя задержка и лишний слой, который сам по себе заметен.
* **Звонки не деградируют.** Голос и видео чувствительны к задержке, лишний
  прыжок через другую страну им противопоказан.

Как исключаем, по платформам:

| Платформа | Механизм |
|---|---|
| **Android** | `VpnService.addDisallowedApplication(<наш пакет>)` — система сама уводит трафик приложения мимо tun |
| **Десктоп (tun)** | Явные маршруты через физический шлюз для: домашнего сервера, relay звонков, узлов-тайников, входных узлов VPN. Адреса резолвятся при старте и переустанавливаются при смене сети |
| **Запасной режим (прокси)** | Клиент мессенджера просто не использует локальный вход |

Честно про цену: провайдер по-прежнему видит, что вы обращаетесь к своему
homeserver'у (но не видит содержимое — оно E2E и завёрнуто в наш стелс-транспорт).
Прятать сам факт использования Призрака внутри VPN — отдельная задача; при
желании это можно будет включить галочкой позже, с оговоркой про петлю
(мессенджер пойдёт в туннель, а сам туннель — мимо себя).

## 7b. Роли узлов и этапность

Роли разведены намеренно, потому что риск у них разный:

| Роль | Что делает | Чей IP видят сайты | Риск оператора |
|---|---|---|---|
| **Приманка / промежуточный** | Пропускает **зашифрованный** трафик насквозь, не знает назначения | Ничей — наружу ничего не выходит | Низкий |
| **Выход** | Открывает соединения в открытый интернет | **Оператора** | Высокий: жалобы, чёрные списки, вопросы |

**На старте (сейчас):** и приманки, и выходы — только наши собственные серверы.
Пользовательские узлы выключены.

**Заложено на будущее:** архитектура с самого начала не различает «наш» и «чужой»
узел — учёт трафика, билеты и награды написаны обобщённо. Включение
пользовательских узлов — это переключатель политики, а не переписывание:

* `allowCommunityRelays` — разрешить чужие приманки/ретрансляторы;
* `allowCommunityExits` — разрешить чужие выходы (по умолчанию **выключено**).

Когда будем включать — правила уже определены:
* на телефоне роль «выход» недоступна вовсе, только ретранслятор;
* включение выхода — отдельное осознанное подтверждение с прямым текстом о том,
  что чужой трафик пойдёт с вашего адреса;
* по умолчанию только Wi-Fi и зарядка, с лимитом трафика.

## 7c. Страны: реестр и честная проверка

Пользователь выбирает страну выхода — значит, страну нужно знать **достоверно**,
а не со слов узла.

**Как определяем:**
1. Узел при регистрации сообщает свою страну (заявка).
2. Реестр проверяет её сам: берёт **IP, с которого узел реально подключился**
   (подделать его на уровне TCP нельзя) и смотрит по офлайновой базе GeoIP.
   Внешние сервисы в момент работы не дёргаем — никаких лишних запросов.
3. Не сошлось — узел помечается как непроверенный и в список стран не попадает.
4. Проверка повторяется периодически: у серверов меняются адреса.

**Что хранит реестр по узлу:** код страны (`FR`, `DE`, `SE`…), номер автономной
системы (чтобы не показывать пять «разных» узлов одного хостера), задержку,
загрузку, время последней проверки.

**Что видит пользователь:** список стран с флагами, задержкой и загрузкой.
Страны без живых проверенных узлов не показываются вовсе.

## 7c-1. Рейтинг узлов: оценки от пользователей

Пользователь может поставить узлу **от 1 до 5 звёзд** — оценку качества работы.
Средняя выводится рядом со страной в списке выбора: например, **4.35 из 5**.

**Что показываем в списке стран:**

```
🇫🇷  Франция     ★ 4.35   45 мс   загрузка 30%
🇸🇪  Швеция      ★ 4.82   62 мс   загрузка 12%
🇩🇪  Германия    ★ 3.10   38 мс   загрузка 80%     ← видно, что с узлом беда
```

Если в стране несколько узлов, показывается рейтинг страны (среднее по её
живым узлам), а внутри страны клиент сам выбирает узел получше.

**Как считается, чтобы цифра была честной:**

* **Оценка привязана к сессии.** Оценить можно только тот узел, через который
  реально работал, и не чаще одного раза в сутки. Иначе рейтинг накручивается
  за минуту.
* **Свежесть важнее истории.** Оценки старше 60 дней перестают учитываться:
  узел мог давно почищен и починен, а мог наоборот испортиться.
* **Защита от единичных выбросов.** Пока оценок мало, средняя подтягивается к
  общему среднему по сети (байесовская поправка) — новый узел с одной пятёркой
  не улетает в топ, а с одной единицей не хоронится.
* **Против накрутки.** Одна оценка = один аккаунт + один узел + сутки; оценки
  от аккаунтов без оплаченного билета не учитываются.

**Автоматика важнее звёзд.** Рейтинг — это мнение людей, но выбор узла всё
равно опирается прежде всего на измеримое: задержку, потери, аптайм и загрузку.
Звёзды — дополнительный сигнал и способ быстро заметить то, что метрики не
ловят (например, узел, чей IP забанен на половине сайтов).

**Совсем плохие узлы уходят сами:** рейтинг ниже порога (например, 2.5 при
достаточном числе оценок) — узел перестаёт выдаваться новым пользователям, а
оператору идёт уведомление.

## 7d. Переключение страны на лету

Переключение сделано так, чтобы не было провала связи:

1. Пользователь выбирает **Швецию** вместо **Франции**.
2. Клиент **сначала поднимает** сессию до шведского выхода (через приманку) и
   ждёт готовности.
3. Только потом переводит маршрутизацию: **все новые** соединения идут в Швецию.
4. Французской сессии даётся короткая отсрочка (несколько секунд), чтобы
   докачались уже начатые запросы, затем она закрывается.

Так работает принцип «сначала подключись, потом отключись» — трафик не встаёт
в момент переключения.

**Что пользователь должен понимать:** уже открытые соединения (большая загрузка,
видеозвонок в стороннем приложении) при смене страны оборвутся — потому что
меняется IP-адрес. Это неизбежно и одинаково у всех VPN; мы просто честно
предупреждаем в интерфейсе, а не делаем вид, что переключение бесшовное.

## 7e. Живучесть: проверка узла и автоподхват

**Пинга не будет.** ICMP-эхо — плохой инструмент по трём причинам: его режут
на половине маршрутов, он ходит мимо нашего туннеля (то есть меряет не то, что
нам нужно), и он рисует цензору отдельный опознаваемый узор «клиент регулярно
стучится на такой-то адрес». Никаких служебных портов «для проверки» на узлах
тоже нет — открытый порт статуса это подарок сканеру.

Проверяем **изнутри уже установленной сессии**, теми же кадрами, что и данные.

### Как меряем

1. **Пассивно — в первую очередь.** Мы и так видим по живому потоку:
   доходят ли ответы, какая задержка круга, сколько кадров потерялось,
   какая скорость. Пока трафик идёт — отдельные проверки не нужны вовсе.
2. **Кадр-дыхание.** Когда данных нет, туннель и так шлёт поддерживающие
   кадры по расписанию профиля «тихий фон» (см. §4) — они же служат проверкой
   живости. Отдельного «пингового» кадра нет: узел отвечает таким же
   неотличимым кадром, размер и пауза берутся из того же распределения.
   Снаружи это выглядит как обычная открытая вкладка сайта.
3. **Проверка сквозная, а не до приманки.** Ответ формирует **выходной**
   узел, а не российская приманка. Иначе «всё живо» показывало бы первый
   прыжок при мёртвом втором.

### Когда считаем узел отвалившимся

| Признак | Порог | Что делаем |
|---|---|---|
| Нет ответа на кадры-дыхания | 3 подряд, ~10 сек | Переключаемся |
| Обрыв несущей (TCP/H2 закрылся) | сразу | Пробуем поднять заново 1 раз, дальше переключаемся |
| Задержка круга | > 2 сек в среднем за 30 сек | Помечаем «плохой», ищем замену **в фоне** |
| Скорость | обвал более чем втрое от собственного среднего | То же — фоновый поиск замены |

Разница важная: **мёртвый** узел меняем немедленно, **медленный** — только
когда нашли лучше, чтобы не дёргать пользователя туда-сюда.

### Куда переключаемся

Порядок строго такой:

1. **Другой узел той же страны** — лучший по рейтингу (§7c-1) из тех, что
   клиент ещё не пробовал в этой сессии.
2. Если в стране живых узлов больше нет — **соседняя страна из списка**.
   «Соседняя» берётся из таблицы близости в реестре: сначала географически и
   сетево близкие (для Франции — Германия, Нидерланды, Бельгия), потом
   остальные по рейтингу. Таблицу ведёт реестр, клиент её просто получает —
   значит правила можно править без обновления приложений.
3. Если не отвечает вообще ничего — маскировка **не выключается молча**.
   Клиент остаётся в состоянии «ищу узел» и **не пускает трафик в обход
   туннеля**: лучше нет связи, чем внезапно голый IP. Пользователь видит это
   явно и может выключить маскировку сам.

Само переключение делается по правилу «сначала подключись, потом отключись»
(§7d) — если старый узел ещё жив, но плохой. Если он уже мёртв, ждать нечего:
поднимаем новый сразу.

### Что видит пользователь

* Молча меняем узел **внутри выбранной страны** — только строчка в журнале
  подключения.
* Смена **страны** (когда своя кончилась) показывается уведомлением:
  «Франция недоступна — переключил на Германию», с кнопкой «выбрать другую».
  Тихо менять страну нельзя: человек мог выбрать её осознанно.
* Каждое вынужденное переключение записывается узлу в статистику надёжности и
  влияет на его рейтинг (§7c-1) — узел, с которого постоянно убегают, сам
  уходит вниз списка.

## 9. Честно о рисках

* **Гарантий не даёт никто.** Любой обход — это гонка. Мы закладываем
  живучесть (несколько несущих, ротация адресов, быстрый выпуск контрмер),
  но «навсегда непробиваемо» не бывает.
* **Проверять надо в поле.** Лабораторный детектор и симулятор DPI ловят
  грубые ошибки, но финальное слово — за реальными тестами из РФ на разных
  операторах.
* **Выходной узел видит назначение.** Он не видит, кто вы, но знает, к какому
  сайту идёт соединение. Поэтому HTTPS внутри туннеля обязателен — и он есть.
* **Приманка в РФ юридически уязвимее выхода.** Поэтому она принципиально
  «глупая»: не хранит логов, не знает назначения, легко заменяется.
