# Prizrak — архитектурный проект

Децентрализованный мессенджер для свободного общения: федерация в духе Matrix,
сквозное шифрование с открытым/закрытым ключом и stealth-транспорт для звонков,
невидимый для DPI/ТСПУ.

Документ описывает концепцию целиком. Рядом лежит рабочий прототип
(`packages/`, `demo/`), который уже демонстрирует все три опорных механизма на
живом коде. Прототип — доказательство осуществимости, не продакшен.

---

## 1. Философия и три опоры

Три вещи, которые пользователь назвал ключевыми, и на которых стоит вся система:

1. **Федерация и лёгкое разворачивание.** Нет единого центра. Любой поднимает
   свой сервер на своём домене за пару минут, и его пользователи сразу общаются
   с пользователями других серверов — как электронная почта или Matrix.
2. **Сквозное шифрование (E2E).** Сервер — это тупой ретранслятор запечатанных
   конвертов. Прочитать переписку не может ни владелец сервера, ни провайдер,
   ни тот, кто сервер изъял. Ключи есть только у собеседников.
3. **Транспорт, невидимый для DPI.** Звонки и трафик должны выглядеть как
   обычный веб-сёрфинг, чтобы ТСПУ не мог их опознать и заблокировать.

Всё остальное (группы, файлы, статусы, боты) — надстройки над этими тремя.

## 2. Общая архитектура

```
   Устройство Alice                                  Устройство Bob
 ┌───────────────────┐                             ┌───────────────────┐
 │  Клиент Prizrak   │                             │  Клиент Prizrak   │
 │  • OpenPGP-паспорт │                             │  • OpenPGP-паспорт │
 │  • Double Ratchet  │                             │  • Double Ratchet  │
 │  • Stealth-клиент  │                             │  • Stealth-клиент  │
 └─────────┬─────────┘                             └─────────┬─────────┘
           │  Client–Server API (запечатанные конверты)      │
 ┌─────────▼─────────┐        Server–Server         ┌────────▼──────────┐
 │  Homeserver a.org │◀────── (федерация) ─────────▶│  Homeserver b.org │
 │  видит только:    │      запечатанные конверты   │  видит только:    │
 │  кто→кому + шифр   │                             │  кто→кому + шифр   │
 └───────────────────┘                             └───────────────────┘
           ▲                                                 ▲
           └──────── Stealth-транспорт для ЗВОНКОВ ──────────┘
             (медиа поверх «настоящего HTTPS», в обход DPI)
```

Два независимых канала:

- **Канал сообщений** идёт через homeserver'ы (store-and-forward, работает даже
  когда собеседник оффлайн). Сервер хранит запечатанные конверты до доставки.
- **Канал звонков** — по возможности прямой P2P или через relay, но всегда
  завёрнутый в stealth-транспорт. Медиа не оседает на сервере.

Ключевой инвариант: **сервер оперирует только маршрутными метаданными
(`from`, `to`, время) и зашифрованным `payload`.** Содержимого он не знает.
В прототипе это видно буквально — `demo/demo.js` печатает то, что лежит в inbox
на сервере: там только шифртекст.

## 3. Федерация (по мотивам Matrix, но проще)

### 3.1. Идентификаторы и discovery

- Пользователь: `@localpart:domain` (например `@alice:a.org`). Домен —
  «домашний сервер», отвечающий за этого пользователя.
- Discovery: `GET https://domain/.well-known/prizrak/server` → `{ base_url }`.
  Так любой сервер узнаёт, куда слать конверты для чужого домена (аналог
  `.well-known/matrix/server`). В прототипе для локальной сети вместо DNS
  используется реестр `PRIZRAK_RESOLVER`.

### 3.2. Два API

**Client–Server API** (клиент ↔ свой homeserver):

| Метод | Путь | Назначение |
|------|------|-----------|
| POST | `/_prizrak/client/v1/register` | опубликовать профиль и prekey-bundle |
| GET  | `/_prizrak/client/v1/bundle?userId=` | получить prekey-bundle (в т.ч. чужого домена — через федерацию) |
| POST | `/_prizrak/client/v1/send` | отправить запечатанный конверт |
| GET  | `/_prizrak/client/v1/inbox?userId=` | забрать входящие |

**Server–Server API** (homeserver ↔ homeserver):

| Метод | Путь | Назначение |
|------|------|-----------|
| POST | `/_prizrak/federation/v1/send` | принять конверт для локального пользователя |
| GET  | `/_prizrak/federation/v1/bundle?userId=` | отдать prekey-bundle своего пользователя |

Когда `@alice:a.org` пишет `@bob:b.org`, сервер `a.org` видит домен получателя,
находит `base_url` для `b.org` и пересылает конверт на его federation-эндпоинт.
Это уже работает в `demo/demo.js`.

### 3.3. Чем сознательно проще Matrix

Matrix — это реплицируемый граф состояния комнаты с разрешением конфликтов
(state resolution), что мощно, но тяжело. Для мессенджера «как Telegram» это
избыточно. Prizrak берёт модель федерации Matrix, но:

- сообщения — это поток запечатанных событий с доставкой store-and-forward, без
  полной репликации DAG-графа состояния между серверами;
- групповое состояние решается на уровне E2E-группы (MLS, см. ниже), а не на
  уровне открытого серверного стейта.

### 3.4. Что нужно добавить к прототипу для прода

Realtime-доставка (WebSocket/long-poll вместо polling `inbox`), подпись
server-to-server запросов ключом сервера, устойчивые очереди и ретраи
федерации, rate-limit и анти-спам, хранение в PostgreSQL/SQLite вместо JSON,
медиарепозиторий (загрузка файлов — тоже E2E, сервер хранит шифрованные блобы),
модерация и списки блокировок на уровне сервера.

## 4. Сквозное шифрование: честный разбор OpenPGP и итоговый гибрид

Пользователь просил встроить OpenPGP с открытым/закрытым ключом. Это правильная
интуиция про асимметричную криптографию — но если шифровать OpenPGP **сам поток
сообщений**, получится слабый мессенджер. Поэтому OpenPGP используется там, где
он силён, а поток сообщений защищается современным ратчетом.

### 4.1. Почему «чистый PGP-мессенджер» — плохая идея

- **Нет forward secrecy.** В PGP все сообщения к вам шифруются на один и тот же
  долговременный ключ. Утёк ключ один раз — расшифровывается вся история
  переписки за годы. У ратчета для каждого сообщения — свой одноразовый ключ.
- **Нет post-compromise security.** После компрометации PGP не «самолечится».
  Double Ratchet при следующем DH-обмене восстанавливает секретность.
- **Метаданные и «отравленные» подписи.** Классический OpenPGP тащит id ключей,
  версии, длинную цепочку опций; исторически с ним много проблем формата и UX.
- **Управление ключами.** Ротация, отзыв и «правильный» выбор ключа в PGP —
  главный источник ошибок у обычных пользователей.

Это не мнение против асимметрики — это про то, что поток сообщений требует
эфемерности, которой у долговременного PGP-ключа нет.

### 4.2. Где OpenPGP реально уместен и остаётся в проекте

- **Паспорт личности / корень доверия.** Долговременный OpenPGP-ключ — это
  устойчивая личность. Его отпечаток пользователи сверяют лично (safety number).
- **Подпись эфемерных ключей.** Все X25519 prekeys подписываются OpenPGP-ключом.
  Именно эта подпись защищает от MITM при установке сессии. В прототипе подмена
  prekey-bundle отвергается по OpenPGP-подписи (см. `demo/crypto-test.js`).
- **Оффлайн-конверты «в архив».** Инвайты, пуш-нагрузка, резервные сообщения без
  живой сессии — здесь классическое OpenPGP-шифрование к публичному ключу самое
  то (`pgpEncrypt`/`pgpDecrypt` в `identity.js`).

### 4.3. Итоговая схема (то, что в коде)

```
OpenPGP-ключ (долговременный)  ──подписывает──▶  X25519 identity + prekeys
                                                          │
                                             X3DH: первый общий секрет
                                                          │
                                              Double Ratchet (поток 1:1)
                                    forward secrecy + post-compromise security
```

- **X3DH-lite** (`ratchet.js`): инициатор из проверенного bundle получателя и
  своего эфемерного ключа выводит общий секрет; получатель восстанавливает его
  из своих приватных ключей.
- **Double Ratchet** (`ratchet.js`): X25519 для DH-ратчета, HKDF-SHA256 для
  root-цепочки, HMAC-SHA256 для symmetric-цепочек, ChaCha20-Poly1305 как AEAD.
  Поддержана доставка не по порядку (skipped message keys).

### 4.4. Группы: MLS (RFC 9420)

Для 1:1 и небольших групп достаточно попарного Double Ratchet. Для больших
групп попарные сессии не масштабируются (O(n) шифрований на сообщение). Здесь
берётся **MLS — Messaging Layer Security, RFC 9420**: групповой E2E со
стоимостью операций O(log n) на изменение состава, forward secrecy и
post-compromise security на уровне группы. MLS спроектирован в том числе под
федерацию, что идеально ложится на нашу модель. Практический путь — библиотека
OpenMLS (Rust) через FFI/WASM.

### 4.5. Верификация и защита от MITM

Сервер, раздающий prekey-bundle, теоретически может подсунуть чужой ключ.
Защита многослойная: (1) prekeys подписаны OpenPGP-паспортом; (2) пользователи
сверяют отпечаток паспорта лично (safety number / QR); (3) для прода — публичный
**key transparency** лог (append-only, как CONIKS/Key Transparency), чтобы
подмена ключа была публично обнаружима.

## 5. Транспорт: невидимость для DPI/ТСПУ

Самая сложная и самая нужная часть. Пользователь верно заметил: **STUN не
годится**. Разберём почему и что вместо него.

### 5.1. Почему обычный WebRTC-звонок режется ТСПУ

DPI ищет фиксированные сигнатуры в начале пакетов. У WebRTC их две очевидные:

- **STUN/ICE**: в пакете на смещении 4 стоит magic cookie `0x2112A442` открытым
  текстом. Опознаётся мгновенно.
- **DTLS-SRTP** (сам медиапоток): record type `22` + версия `0xFEFD` — тоже
  чёткая сигнатура.

В прототипе игрушечный DPI-классификатор (`dpi-analyzer.js`) ловит оба случая,
и `demo.js` это печатает. Отсюда: маскировать нужно не только «сигналинг», а
весь транспорт целиком.

### 5.2. Принцип решения: не имитировать HTTPS, а быть им (Reality)

Лучшее, что сейчас реально работает против ТСПУ, — подход **VLESS + Reality
(XTLS)**. Его идея контринтуитивна: не подделывать TLS, а провести **настоящий
TLS 1.3-хендшейк с настоящим публичным сайтом-прикрытием**. Тогда «подделывать
нечего»:

- на проводе — байт-в-байт валидный TLS 1.3 к реальному домену (например, к
  крупному CDN), с реальным сертификатом, проходящим Certificate Transparency;
- TLS-фингерпринт клиента совпадает с настоящим браузером (uTLS: Chrome/Firefox);
- свой клиент доказывает право на туннель **скрытым токеном внутри уже
  зашифрованного канала** (в Reality — shortId + X25519 в key_share);
- **probe-resistance**: если по адресу постучится цензор без валидного токена,
  сервер прозрачно отдаёт ему настоящий сайт-прикрытие. Аномалии нет —
  блокировать не за что.

Prizrak применяет тот же принцип и к звонкам: сигналинг и медиа идут единым
потоком внутри такого «настоящего HTTPS», без STUN и без DTLS-сигнатур.

### 5.3. Что демонстрирует прототип

`packages/transport/` — рабочая мини-версия принципа:

- **Настоящий TLS наружу.** Туннель поднят на `node:tls`; на проводе — валидные
  TLS-записи (`0x16.../0x17...`). DPI-классификатор помечает их как обычный
  HTTPS и пропускает.
- **Скрытый токен внутри TLS.** Право на туннель клиент доказывает зашифрованным
  токеном уже после установки TLS — снаружи не виден.
- **Probe-resistance.** Стук без токена → сервер отдаёт правдоподобную
  страницу-обманку («It works / Edge node online») и закрывает соединение.
- **Обфускация длин.** Медиакадры дополняются случайным паддингом, чтобы скрыть
  характерный размер аудиопакетов от статистического DPI.

Запуск: `npm run demo:transport`.

### 5.4. Что нужно добавить к прототипу для настоящей стойкости

Прототип показывает принцип, но честный продовый stealth-транспорт требует:

- **Настоящий Reality-режим**: SNI и апстрим — живой популярный сайт, реальный
  сертификат, uTLS-фингерпринт браузера, XTLS-Vision против детекта «TLS в TLS».
- **UDP-путь с низкой задержкой для звонков**: маскировка под **QUIC/HTTP-3**
  (MASQUE, RFC 9298 — туннелирование UDP поверх HTTP), потому что чистый TLS
  поверх TCP добавляет задержку и head-of-line blocking, вредные для голоса.
- **Несколько взаимозаменяемых транспортов и авто-переключение**: Reality-TCP,
  QUIC-masque, WebSocket-over-TLS, при глухой блокировке — домен-фронтинг и
  мосты (bridges) по аналогии с Tor/Snowflake.
- **Ротация точек входа**: раздача адресов relay по «мостовой» модели, чтобы их
  нельзя было разом внести в чёрные списки.
- **Разнесение сигналинга и медиа** так, чтобы оба выглядели как независимые
  HTTPS-сессии к правдоподобным хостам.

### 5.5. Про голос: кодек и relay

Аудио — Opus (низкий битрейт, устойчив к потерям), поверх SRTP, но всё это —
**внутри** stealth-туннеля, а не как открытый WebRTC. Топология: прямой P2P,
если получается пробить NAT незаметно; иначе TURN-подобный relay, тоже
завёрнутый в stealth. Групповые звонки — через SFU (как LiveKit в статье про
Matrix), где SFU стоит за stealth-фронтом.

## 6. Рекомендуемый стек

| Слой | Прототип (сейчас) | Продакшен (рекомендация) |
|------|-------------------|--------------------------|
| Крипто-примитивы | `@noble/*`, `openpgp` | те же + аудит; OpenMLS (Rust) для групп |
| Ратчет | своя реализация (учебная) | libsignal / зрелая реализация Double Ratchet |
| Homeserver | Node.js + `node:http` | Go или Rust (производительность, память), PostgreSQL |
| Realtime | polling `inbox` | WebSocket, серверные пуши |
| Stealth-транспорт | `node:tls` + токен + обманка | Xray-core (Reality/XTLS-Vision), QUIC/MASQUE |
| Звонки | демо-кадры в туннеле | Opus + SRTP внутри stealth, SFU за фронтом |
| Клиенты | CLI-библиотека | десктоп/мобайл (напр. общий Rust-кор + нативный UI) |

Почему Rust/Go для сервера: федеративный узел держит много соединений и должен
быть экономным и безопасным по памяти; крипто-кор на Rust удобно переиспользовать
на всех платформах через FFI/WASM.

## 7. Модель угроз (кратко)

| Противник | Что может | Чем защищаемся |
|-----------|-----------|----------------|
| Владелец сервера / изъятие сервера | видит метаданные и шифртекст | E2E: контента нет; forward secrecy у истории |
| Провайдер / ТСПУ (пассивный DPI) | видит трафик на проводе | Reality: неотличимо от HTTPS к живому сайту |
| Цензор (активное зондирование) | стучится на сервер | probe-resistance: отдаём сайт-обманку |
| MITM при обмене ключами | подменяет prekey | OpenPGP-подпись prekeys + safety number + KT-лог |
| Компрометация устройства | читает текущие ключи | post-compromise security ратчета/MLS |

Честные ограничения: E2E не прячет **сам факт** переписки от вашего homeserver'а
(метаданные «кто с кем и когда»). Их снижают минимизацией логов, sealed-sender и
разнесением сигналинга. Абсолютной невидимости не существует — цель в том, чтобы
блокировка и деанонимизация стоили противнику непропорционально дорого.

## 8. Дорожная карта

1. **MVP (есть в прототипе).** Федерация двух серверов, E2E 1:1 (OpenPGP-паспорт
   + X3DH + Double Ratchet), демонстрация stealth-транспорта, Docker-разворот.
2. **Надёжный обмен.** WebSocket-доставка, подпись S2S, PostgreSQL, медиа-хранилище
   (шифрованные блобы), пуш-уведомления.
3. **Группы.** Интеграция MLS (OpenMLS), групповые комнаты, роли, приглашения.
4. **Звонки.** Opus/SRTP внутри stealth; настоящий Reality/XTLS-Vision; QUIC/MASQUE;
   relay/SFU за фронтом; авто-переключение транспортов.
5. **Устойчивость к блокировкам.** Мостовая раздача точек входа, домен-фронтинг,
   Snowflake-подобные волонтёрские прокси.
6. **Доверие и удобство.** Key transparency лог, верификация по QR, восстановление
   аккаунта, кроссплатформенные клиенты.
7. **Экосистема.** Мосты (Telegram/Matrix/XMPP), боты, простой one-command деплой.

## 9. Юридическое и этическое замечание

Инструменты обхода цензуры защищают свободу слова и приватность, но их легальность
различается по юрисдикциям — в частности, в РФ регулирование средств обхода
блокировок ужесточается. Проект стоит развивать как **опенсорс для приватности и
свободы общения**; конечные пользователи сами отвечают за соблюдение применимого
к ним закона. Криптографию не стоит «катать свою» — за пределами прототипа нужны
проверенные библиотеки и независимый аудит.

```bash
npm install

node demo/crypto-test.js # самотест крипто: X3DH, ратчет, out-of-order, анти-MITM

```

Прототип намеренно компактен и читаем — это каркас и доказательство концепции,
на котором дальше наращивается продовая система по разделам 3–8.
